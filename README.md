# quant-engine-py

nanobind bindings for [quant-engine](https://git.sr.ht/~jzhex/quant-engine).
**Python drives the engine; Python does not participate in it.**

Tracked as PER-222 / S1 (PER-239).

## The boundary

Python may start a run and read its results. Python may **not** be
called from inside `Engine::run()`.

That is a correctness property, not a preference. The engine's hot loop
is allocation-free with no virtual dispatch — verified by a counting
allocator in the engine's own `tests/test_zero_alloc.cpp` — and the
performance targets in its `CLAUDE.md` assume it. A per-bar Python
callback takes the GIL ~2500 times per backtest and allocates on every
one. The binding that lets someone write a strategy in Python is the
binding that silently voids every number in that table.

So there is no callback surface here, and adding one is a design
change, not a feature.

## Why a separate repo

The engine's `CLAUDE.md` says so under anti-patterns. This repo honours
that rule rather than amending it: the engine stays pure C++, its
`vcpkg.json` and tech-stack table are untouched, and the NixOS
deployment host never grows a Python build chain.

## Version alignment, which is the real cost

Two repos, no CI (deliberate), and a C++ API with no stability
guarantee. The failure mode is a binding compiled against one engine
and read as though it spoke for another: it imports, it runs, and it
returns *subtly different numbers*. Nothing downstream can detect that.

Three things hold the line:

1. **The engine is a submodule pinned at a TAG**, never a branch.
   Consequence, by construction: the bindings lag the engine by one
   release. A commit landing on the engine's `main` today is not here
   until the next tag.
2. **The extension carries the version and commit it was compiled
   from** — the version read from the engine's own generated
   `qe::KVersion`, not a literal this repo maintains. At import, if the
   submodule source is present, its current commit is compared and a
   mismatch **raises**. Not warns: the whole point is that the mismatch
   is invisible in the results.
3. **A parity golden generated by the engine**, not by a second
   implementation. `tools/gen_ic_golden.cpp` links `qe::qe` and writes
   both the input and the expected output; `tests/test_parity.py`
   asserts exact equality. Regenerate deliberately with
   `tools/regen-golden.sh` — a moved golden is a claim that the engine
   changed.

## Build

Needs `VCPKG_ROOT` (the engine uses vcpkg in manifest mode) and a real
Python — **not** a 3.14 alpha; the engine repo already lost a day to
that one segfaulting mkdocs.

```bash
git submodule update --init --recursive
~/.pyenv/versions/3.12.2/bin/python -m venv .venv
.venv/bin/pip install scikit-build-core nanobind
export VCPKG_ROOT=$HOME/vcpkg
.venv/bin/pip install --no-build-isolation -e .
.venv/bin/python -m unittest discover -s tests -v
```

The engine's own manifest defaults to `gui` + `tests` + `benchmarks`;
this build disables all three, so GLFW/ImGui/ImPlot/Catch2/Google
Benchmark are never built to produce a Python module.

## Surface

The standalone analytics (S1 + S5). Everything here takes plain series
and returns plain results — no config machinery, no provenance, no
engine hot loop. Bars/numpy marshalling is S3 and the `.qe` path is S4.

```python
import qe
qe.engine_version          # '0.4.2', from the engine's own header

qe.ic_analysis(factor=..., returns=..., horizon=20)
qe.rolling_ic_analysis(factor=..., returns=..., timestamps=...,
                       horizon=20, window_bars=120, step_bars=20)
qe.long_short_backtest(factor=..., returns=..., timestamps=...,
                       quantiles=5, rebalance_bars=21,
                       holding_periods_per_year=12.0, commission_bps=5.0)

qe.kahan_sum(xs)
qe.sharpe(rets, periods_per_year=252, rf_annual=0.0)
qe.sortino(rets, periods_per_year=252, rf_annual=0.0)
qe.total_return(timestamps_ns=..., equity=...)
qe.cagr(timestamps_ns=..., equity=..., periods_per_year=252)
qe.max_drawdown(timestamps_ns=..., equity=...)
```

Two things worth knowing before you read a number:

**Drawdown has two sign conventions in `qe::analytics`, and this is not
the binding's doing.** `max_drawdown` documents *a positive fraction*
(0.25 = gave back a quarter), while `LongShortResult.max_dd` documents
*the most negative excursion* and reports e.g. `-0.202`. Compare like
with like. A test pins both so no future change quietly normalises one
into the other.

**Degenerate input is reported, not raised.** `ic_analysis` answers a
shape mismatch with `n_obs == 0`; `rolling_ic_analysis` with an empty
`windows`; the `metrics` curve functions with `NaN` below two points
rather than `0.0`, because `0.0` reads as a flat curve and `NaN` reads
as no answer. `long_short_backtest` counts dropped rebalances in
`n_skipped` — read it before you read `sharpe`.

The `metrics` functions take parallel `timestamps_ns` / `equity` arrays
rather than a bound `EquityPoint` list: the caller side is numpy, the
engine's storage rule is struct-of-arrays, and a list-of-structs is the
one shape neither side wants. Mismatched lengths raise rather than zip
to the shorter one, which would misdate every point after the gap.

## Why nanobind and not pybind11

Measured, not assumed. Same function, same flags, same Python:

| | pybind11 | nanobind |
|---|---|---|
| binding TU compile | 2.97 s | **0.54 s** |
| binding TU object | 322.4 KiB | **20.2 KiB** |
| final `.so` | 299.0 KiB | 266.0 KiB |

pybind11 is header-only, so its 2.97 s is paid by every binding TU
forever; nanobind's runtime compiles once. Both produced identical
results across all 16 fields. Full numbers and methodology are in
PER-239.
